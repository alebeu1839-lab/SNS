## 設計上の判断と理由

### 1. 収集スコープの定義を1箇所に集約した

`agent/scopes.py` の `SCOPES` が、エージェントの収集判定・DBの同意レコード・
画面の説明文のすべての出所です。「画面には書いてあるが実際は別のものを取っている」
という状態が構造的に起きないようにしています。

### 2. 機密情報は「保存前」に落とす

`Redactor` はコレクタとDBの間に必ず入り、コレクタからDBへの直通経路はありません。
削除ではなく**最初から保存しない**ため、後からの漏洩経路が残りません。
破棄した事実は `redaction_stats` に件数と理由だけを記録します（内容は残しません）。

キー内容・クリップボードの中身・本文といった項目は、
「マスクする」のではなく**受け取ったら捨てるフィールド**として実装しています
（`privacy.Redactor.apply` の forbidden リスト）。

### 3. 作業の切れ目をデータから推定する

固定しきい値（例: 60秒空いたら別作業）は人によって外れます。
`pattern.estimate_block_gap` はセグメント間の「間」の分布に Otsu 法を適用し、
作業内の小休止と作業間の切れ目を分ける境界を推定します。

### 4. 業務の発見を「頻度 × 系列構造」で行う

アプリの使用時間ランキングでは業務は見つかりません。実装は次の2段構えです。

1. 作業ブロックの手順シグネチャで直接クラスタリング（支持度が足りるもの）
2. 支持度が足りないブロックについては、ブロック内の連続部分列を可変長で
   マイニングし、割り込みが入った回に埋もれた反復を拾う

さらに `normalize_clusters` が周期的なシグネチャ（A→B→A→B）を1周期へ畳み込み、
同じ業務が二重に数えられるのを防ぎます。

### 5. LLM は「言語化」に使い、「数値」には使わない

- 業務名・説明・手順の文章化、実装方針・リスク文言 → Claude（任意）
- 発生回数・所要時間・削減時間・難易度スコア → 計測値からの決定論的算出

数字をLLMに作らせないため、経営判断に使う値の根拠が常に追跡可能です。
`ANTHROPIC_API_KEY` が無い場合もルールエンジンで全機能が動作します。

### 6. SaaS 化を見据えたデータ分離

全テーブルが `company_id` を持ち、取得系は企業でフィルタします。
ID は UUID(TEXT) 固定で、Postgres へ移す際に型の変更が発生しません。
生SQLは `storage/` に閉じ込めてあり、上位層はリポジトリ経由でのみアクセスします。

## STEP 2 への接続点

| 引き渡すもの | 場所 |
|---|---|
| 実装対象の候補 | `candidate_decisions.decision = 'automate'` |
| 実装仕様の下書き | `automation_candidates.step2_spec_json` |
| 対象システムと役割 | 同 `systems`（参照元 / 書き込み先、web / desktop） |
| ガードレール要件 | 同 `guardrails`（ドライラン、実行ログ、例外時の人への引き継ぎ） |
| 未確認事項 | 同 `open_questions`（API有無、除外すべき例外パターン） |

## STEP 3（運用・最適化）への接続点

`analysis_runs` に実行ごとの統計（総作業時間・業務数・候補数・削減見込み）が
残るため、自動化の前後で同じ指標を比較できます。
`tasks.total_duration_sec` の推移が、実際に削減できたかの計測値になります。
